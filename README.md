# Benua · Telegram Bot Template

Основа Telegram-бота на Python и aiogram 3 для развития в прикладной продукт: приём заявок, диалоги, интеграции с сервисами и ИИ-помощники.

Проект связан с направлением [Benua — ИИ и разработка цифровых продуктов](https://thebenua.online/): соединять логику, данные и интерфейс вокруг понятного действия пользователя. Здесь интерфейсом служит Telegram.

Это стартовый каркас. Сейчас бот отвечает на `/start`; остальные сценарии добавляются под конкретную задачу.

## Что уже есть

| Компонент | Состояние в репозитории |
| --- | --- |
| Запуск бота | Асинхронный polling через `Dispatcher` |
| Обработка команд | Отдельный роутер с `/start` |
| Конфигурация | `pydantic-settings`, чтение `.env`, токен как `SecretStr` |
| Логи | Стандартный `logging` на уровне INFO |
| PostgreSQL и Redis | Зависимости и сервисы Compose; подключения из Python ещё нет |
| Docker | Заготовка Compose; Dockerfile пока отсутствует |
| ИИ и внешние API | Точки развития; готовых интеграций пока нет |

Нагрузочные тесты, CI и готовность к production этим репозиторием пока не подтверждены.

## Для каких задач развивать шаблон

- **Заявки:** собрать запрос, уточнить детали, показать подтверждение и передать данные ответственному.
- **Диалоги:** провести человека через несколько шагов с возможностью вернуться назад или отменить действие.
- **Сервисные действия:** получить статус заказа, запросить данные из API или отправить уведомление.
- **ИИ-помощник:** принять вопрос, собрать нужный контекст и вернуть ответ в рамках заданной роли.

Это примеры будущих сценариев, а не перечень уже реализованных функций. Для первой версии стоит выбрать один путь от команды до полезного результата.

## Технологии

| Технология | Версия в requirements.txt | Назначение |
| --- | --- | --- |
| aiogram | 3.13.1 | Telegram Bot API, маршрутизация событий |
| pydantic-settings | 2.4.0 | Настройки из окружения и `.env` |
| SQLAlchemy | 2.0.32 | Зависимость для будущего слоя данных |
| asyncpg | 0.29.0 | Асинхронный драйвер PostgreSQL |
| redis | 5.0.8 | Клиент для будущего хранилища состояний |
| loguru | 0.7.2 | Установлен; текущий код использует стандартный `logging` |

Для воспроизводимого старта используйте Python 3.11 и отдельное виртуальное окружение. Обновление закреплённых версий требует отдельной проверки совместимости.

## Структура репозитория

```text
aiogram3-bot-template/
├── config/
│   └── config.py        # Settings и загрузка окружения
├── handlers/
│   └── common.py        # Router и команда /start
├── main.py             # Bot, Dispatcher, logging, polling
├── requirements.txt    # Закреплённые зависимости
├── docker-compose.yml  # Заготовка bot + PostgreSQL + Redis
└── README.md
```

Файл `.env` создаётся локально. Каталогов сервисов, моделей БД и миграций в текущем каркасе ещё нет.

## Как проходит запрос

```text
Telegram → polling → Dispatcher → common.router → cmd_start → ответ
```

При запуске импортируется `settings`, проверяются обязательные переменные, создаются `Bot` и `Dispatcher`, подключается роутер. Затем `start_polling` получает события Telegram.

При расширении обработчик должен отвечать за входные данные и сообщение пользователю. Правила продукта и обращения к внешним системам удобно выносить в отдельные сервисы, чтобы их можно было проверять без Telegram.

## Перед запуском

Понадобятся Git, Python 3.11 с `pip`, доступ к Telegram API и токен бота, созданного через [BotFather](https://t.me/BotFather).

Запускайте команды из корня проекта: `.env` читается относительно текущего рабочего каталога. Для проверки существующей команды `/start` работающие PostgreSQL и Redis не нужны, но строки их подключения обязательны для модели настроек.

Токен даёт доступ к управлению ботом. Не вставляйте его в исходный код, сообщения об ошибках или публичные примеры.

## Установка

```bash
git clone https://github.com/Thebenua/aiogram3-bot-template.git
cd aiogram3-bot-template
python -m venv .venv
```

Активируйте окружение в своей оболочке:

```powershell
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
```

```bash
# Linux / macOS
source .venv/bin/activate
```

Затем установите зависимости:

```bash
python -m pip install -r requirements.txt
```

Если PowerShell блокирует активацию, можно вызывать интерпретатор напрямую: `.\.venv\Scripts\python.exe -m pip install -r requirements.txt`.

## Настройка окружения

Создайте в корне `.env`:

```dotenv
BOT_TOKEN=replace_with_your_botfather_token
DATABASE_URL=postgresql+asyncpg://benua_user:replace_with_local_password@localhost:5432/bot_metadata
REDIS_URL=redis://localhost:6379/0
```

| Переменная | Как используется сейчас |
| --- | --- |
| `BOT_TOKEN` | Передаётся в `Bot`; нужен настоящий токен |
| `DATABASE_URL` | Обязательна в `Settings`, но подключения к БД ещё нет |
| `REDIS_URL` | Обязательна в `Settings`, но Redis storage ещё не подключён |

Адреса БД и Redis в примере — настройки для последующего подключения. Пароль должен совпадать с настройками вашей БД. Добавление других ключей в `.env` согласуйте с моделью `Settings`: неизвестные поля могут вызвать ошибку валидации.

## Локальные файлы и секреты

В репозитории пока нет `.gitignore`. До добавления файлов в индекс исключите хотя бы `.env`, `.venv/`, `__pycache__/` и `*.pyc`: через свой `.gitignore` или локальный `.git/info/exclude`.

Перед коммитом проверяйте `git status` и `git diff --cached`. `SecretStr` скрывает токен в обычном представлении настроек, но вызов `get_secret_value()` возвращает исходное значение — его нельзя логировать.

Если токен уже опубликован, перевыпустите его через BotFather. Удаление строки из последнего коммита не отзывает токен и не убирает его из истории.

## Запуск и первая проверка

```bash
python main.py
```

В PowerShell без активации окружения: `.\.venv\Scripts\python.exe main.py`.

1. Убедитесь, что в терминале появился лог `Starting bot orchestrator...` и нет ошибки подключения.
2. Откройте своего бота и отправьте `/start`.
3. Ожидаемый ответ: «Привет! Я асинхронный Telegram-бот, развернутый из шаблона Benua.»
4. Остановите локальный процесс через `Ctrl+C`.

Запускайте один polling-процесс на токен. Обычный текст пока не обрабатывается: отсутствие ответа на него соответствует текущему коду.

## Docker и инфраструктура

`docker-compose.yml` описывает `bot`, `db` (PostgreSQL 16 Alpine) и `redis` (Redis 7 Alpine). Полный запуск через `docker compose up --build -d` пока не готов: сервис `bot` использует `build: .`, а Dockerfile отсутствует.

Для дальнейшей разработки можно отдельно запустить инфраструктуру:

```bash
docker compose up -d db redis
docker compose ps
```

В текущем Compose пароль PostgreSQL задан как `secure_password`; перед использованием замените его и согласуйте с `DATABASE_URL`. Для локальной инфраструктуры ограничьте опубликованные порты адресом `127.0.0.1`.

Python на хосте обращается к `localhost`. Будущий контейнер бота внутри сети Compose должен обращаться к `db:5432` и `redis:6379`. Смена URL сама по себе не добавляет подключение в код. `depends_on` также не заменяет проверку готовности сервисов и повтор подключения.

## Развитие: приём заявок

Первый полезный сценарий можно построить так: выбор услуги → описание задачи → контакт → проверка введённых данных → подтверждение отправки.

Для реализации понадобятся отдельный роутер, состояния диалога, проверка обязательных полей и сохранение заявки. Предусмотрите отмену, возврат на предыдущий шаг и защиту от повторного создания заявки при повторном нажатии.

Пользователь должен получать подтверждение только после успешного сохранения. Если передача ответственному не удалась, заявку нужно сохранить и отдельно повторить доставку. В стартовом шаблоне этот сценарий ещё не реализован.

## Развитие: PostgreSQL и данные

Наличие SQLAlchemy и asyncpg в зависимостях не создаёт таблицы. Следующий шаг — добавить асинхронный engine, фабрику сессий, модели и миграции схемы.

Для заявок можно начать с идентификатора, Telegram user ID, типа обращения, описания, статуса и времени создания. Контактные данные храните только если они нужны сценарию; заранее определите срок хранения и способ удаления.

Транзакции должны охватывать одно законченное изменение данных. Не держите транзакцию открытой во время долгого обращения к внешнему API. Для постоянного окружения настройте хранение данных PostgreSQL в управляемом томе, резервное копирование и проверку восстановления.

## Развитие: диалоги и Redis

Сейчас `Dispatcher()` создаётся без `RedisStorage`. Состояния многошаговых диалогов в проекте не описаны; стандартное хранилище в памяти не сохраняет их после перезапуска процесса.

Для продолжительных сценариев подключите Redis storage, определите срок жизни состояния и явную команду отмены. Временное состояние диалога и сохранённая заявка решают разные задачи: потеря состояния не должна уничтожать уже принятую заявку.

Проверьте поведение при повторном `/start`, неожиданном сообщении посреди формы, истечении срока состояния и недоступности Redis.

## Развитие: внешние сервисы

Интеграции позволяют связать бота с CRM, системой заказов или собственным API. Для каждой операции определите входные данные, ответ пользователю и поведение при сбое.

- Используйте асинхронный HTTP-клиент и ограничение времени ожидания.
- Проверяйте статус и структуру ответа до использования данных.
- Повторяйте запросы только когда это безопасно; создание заявки или платёж требуют защиты от дублей.
- Показывайте понятное сообщение при недоступности сервиса, а технические детали оставляйте в логах без секретов.

Клиент внешнего сервиса лучше отделить от Telegram-обработчика. Готового HTTP-клиента в этом шаблоне пока нет.

## Развитие: ИИ-помощник

Telegram может стать интерфейсом к помощнику, который отвечает по материалам проекта, уточняет запрос или помогает выбрать следующий шаг. В текущем коде нет LLM-клиента, ключей провайдера или готового агента.

Для первой версии определите роль модели, допустимые источники контекста и ситуации, когда она должна признать отсутствие данных. Затем добавьте отдельный сервис модели с таймаутом, лимитом затрат и ограничением истории диалога.

Ответ модели не должен автоматически давать право на действие. Отправку заявки, изменение данных и другие операции проверяйте обычным кодом; для значимых действий показывайте пользователю подтверждение. До подключения провайдера определите, какие данные разрешено передавать за пределы приложения.

## Если что-то не работает

| Симптом | Что проверить |
| --- | --- |
| `ValidationError` при запуске | Наличие всех трёх ключей, рабочий каталог, лишние поля `.env` |
| Ошибка проверки токена или `Unauthorized` | Настоящий токен BotFather без пробелов; не публикуйте его в issue |
| `ModuleNotFoundError` | Установка зависимостей тем же Python, которым запускается `main.py` |
| `Conflict` при polling | Другой процесс с тем же токеном или активный webhook; остановите другой экземпляр и проверьте webhook |
| Бот не отвечает | Процесс работает, сеть доступна, отправлена именно команда `/start` |
| Сборка Docker не находит Dockerfile | Полная контейнеризация ещё не реализована; используйте локальный запуск |
| Ошибка порта при запуске БД или Redis | Порты 5432/6379 уже заняты; согласуйте новые порты со строками подключения |

Перед обращением за помощью сохраните версию Python, команду запуска и обезличенный traceback. Не прикладывайте `.env`.
